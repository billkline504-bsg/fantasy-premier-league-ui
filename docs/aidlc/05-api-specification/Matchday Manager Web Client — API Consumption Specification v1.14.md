# Matchday Manager Web Client
## API Consumption Specification — Version 1.14

**Inputs:** BRD v1.1, Architecture v1.0, Epic and Feature Backlog v1.0, Feature Behavior Specs v1.0 (all in this repo); Backend OpenAPI Specification v1.0 (vendored alongside this document as `Fantasy EPL League Manager — OpenAPI Specification v1.0.yaml`, copied verbatim from `fantasy-premier-league/docs/aidlc/05-api-specification/`).

---

# 1. Purpose

This client does not author its own API contract — the backend's OpenAPI v1.0 spec (71 endpoints, 23 controllers) is authoritative, and Architecture v1.0 (ADR-003) already commits to generating this client's request/response types directly from it. This document is the **reconciliation pass** the AIDLC pipeline's `05` stage exists for: it maps every UI feature (`F-UI-###.#`) to the exact operations it consumes, and — more importantly — records every place that reading the actual spec, line by line, turned up something the BRD and Architecture had not yet accounted for. Several such findings materially affect earlier documents and are called out immediately in §2 before the routine mapping in §3 onward, growing as each screen gets actually built rather than just planned; the rest of this document is confirmatory (a real mapping) rather than corrective.

# 2. Reconciliation Findings (read this section first)

## 2.1 Draft mutations require an `Idempotency-Key`; roster submission also requires `If-Match` — Architecture v1.0 didn't say so

The spec's `makeDraftPick` and `submitGameweekRoster` operations both take a required `Idempotency-Key` header (client-generated UUID, so a network-retried request can't double-submit — the backend cites `BR-237`). `submitGameweekRoster` additionally takes an `If-Match` header carrying the `ETag` the corresponding `getGameweekRoster` call returned, for optimistic concurrency. Neither requirement was mentioned in Architecture v1.0 (§6.2/§6.3 described the fetch wrapper and mutation hooks generically, with no idempotency- or concurrency-token handling). **This is corrected in Architecture v1.1** (new §6.5) rather than left as a note only in this document, since it changes how two concrete mutation hooks must be implemented. See §5 of this document for the consumption-level detail.

## 2.2 A Draft can be `Paused` — no screen in the BRD accounts for this

`Draft.status` is an enum of `Scheduled | InProgress | Paused | Completed`, and the spec defines `POST /drafts/{draftId}/pause` and `POST /drafts/{draftId}/resume`, both League-Administrator-only. Neither the mock-up nor BRD v1.1 depicts a paused-draft state or a pause/resume control anywhere on Draft Board or Makeup Picks & Timeouts. This is a genuine capability the backend supports that this UI currently has no design for — consistent with how BRD DEC-UI-007 already treats "no source material to interpret" cases, this is **not resolved here**; it's recorded as a new BRD gap (see BRD v1.2, §12 item 12) rather than designed ad hoc in this document. `extendDraftTimer`'s exact request shape (`{ additionalSeconds: integer }`) *is* now known, though, which partially resolves BRD's pre-existing gap #10 (the timer-extension control's existence was known; its input shape wasn't) — the control itself still needs designing.

## 2.3a No phone/SMS field exists anywhere on `UserSelfDto` (found implementing F-UI-001.1, v1.1)

BRD UIR-158 requires the System Profile screen to show the user's email **and phone number**, both masked, citing the mock-up's `+1 (555) •••-0142` row. `UserSelfDto` (the `/users/me` response) has no phone-number field at all, and no other endpoint in the 71-endpoint surface exposes or accepts one. More fundamentally: `NotificationChannel` includes `Sms` as a real, settable per-event preference (`NotificationPreference.channel`), but there is currently no way for a user to ever record the phone number an SMS would be sent to — that preference has no reachable destination. This is a backend data-model gap, not something this client can work around: **the Profile screen renders the SMS/phone contact row as explicitly unavailable** ("No phone number on file — not yet collected by the platform") rather than fabricating a masked placeholder value, and this is logged here rather than silently worked around so it isn't lost. Resolving it is a backend change (adding a phone-number field, presumably to `UserSelfDto` and a corresponding update endpoint), not a UI one.

## 2.3b `ProfileIcon` is an image asset reference, not the mock-up's inline color+emoji badge (found implementing F-UI-001.1, v1.1)

The mock-up's icon catalog is ten hardcoded `{id, bg, label}` entries rendered as colored circles with an emoji/initials label — convenient for a static mock-up, but not what the real contract returns. `ProfileIcon` is `{ profileIconId, name, assetIdentifier, isActive, sortOrder }`; `assetIdentifier` is documented only as a "server-controlled path" with no stated base URL, hosting convention, or format (relative path? absolute URL? something requiring a signed URL?). This client's `IconPicker` renders `assetIdentifier` directly as an `<img src>` — the least presumptuous choice — but this should be confirmed against the running API (or a future Architecture/API-spec revision should pin down the actual convention) rather than assumed correct from the contract alone.

## 2.3c `POST /users/me/reactivate` exists and is unaccounted for — confirmed out of scope, not a new gap

The spec includes a `reactivateUser` operation with no corresponding screen anywhere. Unlike §2.2, this isn't a new finding requiring a BRD update: it's squarely inside the already-deferred authentication/account-lifecycle scope (BRD DEC-UI-007, §12 item 1), so it's noted here for completeness and left there.

## 2.3d No endpoint discovers which EPL seasons exist, or which is "current" (found implementing F-UI-001.3/001.4, v1.2)

`eplSeasonIdentifier` (e.g. `"2026/27"`) only ever appears as an input the caller must already supply (`listGameweeks`'s required query param, `getEplTable`'s path param) or as a field on objects that themselves presuppose it (`Gameweek`, `Season`). There is no `/epl/seasons` listing endpoint or any other way to ask the API "what EPL seasons exist" or "which one is current" independent of already knowing a Fantasy League's own Season history. This client resolves "current" by reading the active League's own Seasons (`GET /leagues/{leagueId}/seasons`) and picking the one with status `InSeason` (falling back through `DraftInProgress`/`Setup`/most-recent) — see `useCurrentEplSeasonIdentifier` in `src/api/hooks/useEpl.ts`. This is defensible for BRD UIR-074 ("must not change when switching leagues") only because there is exactly one real Premier League season running at a time, so the *value* this resolves to is genuinely league-independent even though the *lookup mechanism* isn't. It does **not** extend to historical-season browsing (UIR-076's "at least one prior completed season" tab, UIR-079): different Leagues have different Season histories, so sourcing a "completed seasons" list the same way would make EPL's available tabs vary by active league, a real UIR-074 violation. **Scope decision for this pass**: only the current season is implemented on both EPL Table and Fixtures; historical-season tabs are not built rather than built on a foundation that would violate UIR-074. Properly resolving this needs either a dedicated `/epl/seasons` endpoint or an explicit product decision about how historical EPL seasons should be discovered — flagged here for a future backend/BRD revision, not designed around in this client.

## 2.3e `Fixture` carries no live-match-minute field (found implementing F-UI-001.4, v1.2)

`Fixture` is `{ fixtureId, gameweekId, homeClubId, awayClubId, kickoffTime, status, homeGoals, awayGoals }` — `status: InProgress` tells the client a match is live, and `homeGoals`/`awayGoals` give the current score, but there is no running-clock/minute field anywhere on this schema (the mock-up's `63′` was illustrative, not backed by a real field). This client's `FixtureRow` shows a plain "Live" label next to the current score for an in-progress fixture rather than fabricating a minute count. If match-minute display is wanted later, it needs a backend schema addition, not a client-side workaround (there's nothing to compute it from — kickoff time alone doesn't account for stoppage time, half-time, etc.).

## 2.3f `Club` carries no crest/color field (found implementing F-UI-001.3/001.4, v1.2)

`Club` is `{ clubId, name, shortName }` only — no crest image, no brand color, unlike the mock-up's hardcoded per-club hex colors and the `ProfileIcon` pattern (§2.3b) of at least having *an* asset reference. Every club-badge rendering in this client (`ClubBadge`, used by both the Table and Fixtures views) is a plain neutral badge showing `shortName` as text. Noted here for completeness alongside the other two EPL-screen findings, though this is cosmetic rather than a functional gap.

## 2.3g `FantasyTeam` has no distinct "team name" field — cross-cutting, not scoped to Draft Board (found implementing F-UI-002.1, v1.3)

This is the most consequential finding so far. `FantasyTeam` is `{ fantasyTeamId, leagueMembershipId, seasonId, username, status, createdAt }` — there is no "Iron Wall FC"-style name field anywhere in the schema, and no other endpoint in the 71-endpoint surface adds one. Every team is identified only by `username`, the *owning member's* username — the same value the mock-up also showed separately, right next to a distinct team name, on nearly every screen (the mock-up's `<team-name>` vs. `<mgr>` pattern). This isn't scoped to Draft Board; it invalidates a factual assumption implicit in a large number of BRD UIRs across nearly every screen that displays a team: UIR-037, UIR-039/040, UIR-064/068 ("both the FantasyTeam name and the managing user's username" — there is only one), UIR-091, UIR-100/105, and others not yet reached by an implementation pass. **Resolution adopted for this client, effective immediately and retroactively for Draft Board's already-built order/on-clock/recent-picks panels**: wherever a UIR calls for a "team name," render `FantasyTeam.username` (or `LeagueMembership.username` where no FantasyTeam is in scope) — there is nothing else to show. This is recorded here rather than as a BRD gap, matching DEC-UI-012's precedent: the requirement itself ("show the team's identity") is still correct, only the assumption that a name distinct from username exists is wrong.

## 2.3h Two draft-state fields have inferred, unconfirmed semantics (found implementing F-UI-002.1, v1.3)

Neither is spelled out beyond a field name and type in the spec: (1) `Draft.currentPickIndex` is assumed to be 0-based *within the current round* (not a global pick counter across the whole draft), with even rounds using the reverse of `draftOrder` for that round's actual turn sequence (the snake pattern BR-054/BR-056 describes) — see `resolveOnClockFantasyTeamId` in `src/screens/draft/draftTurn.ts`. (2) There is no "total rounds" field on `Draft` at all; this client derives it from `LeagueConfiguration.initialSquadSize` (Initial Draft) or `.secondaryDraftSelectionsPerTeam` (Secondary Draft), and shows no total at all for a Replacement Draft (which isn't round-based the same way). Both are reasonable, defensible inferences consistent with the backend BRD's own BR-054/BR-056/BR-060 rules, but neither is a *confirmed* contract fact — verify against the running API before relying on either beyond display.

## 2.3i `getDraftPlayerPool` returns undrafted players only — BRD UIR-102/UIR-104's merged available+owned pool isn't buildable as specified (found implementing F-UI-002.1, v1.3)

The operation's own summary says "Remaining **undrafted** players" — confirmed by testing the implementation against it: there is no status/owning-team field, and already-picked players are simply absent from the response, not present-and-flagged. BRD UIR-102 describes a single pool table with a "Status" column distinguishing "Available" from "Owned · <team>"; UIR-104 requires owned players stay visible (de-emphasized), not disappear. Reconstructing this client-side would need cross-referencing `listDraftSelections` (which players are taken) against a second, separately-fetched full player list — and no endpoint returns season-to-date stats (`Min`/`GP`/`Pts`) for players outside a draft's own undrafted-pool response, so an "owned" row would either show fabricated zero stats (indistinguishable from UIR-106's legitimate pre-season zeros — actively misleading) or an inconsistent column set. **Scope decision**: this client's draft pool shows available (undrafted) players only; UIR-104 is not implemented against this API surface as it stands. Resolving it properly needs a backend change — e.g., an `includeOwned` flag on `getDraftPlayerPool` that returns owned rows with the same stats shape and an owning-team field — not a client-side workaround.

## 2.3j The shared `sort` parameter's documented example values don't match either consuming schema's actual field names (found implementing F-UI-002.4, v1.4)

`getDraftPlayerPool` and `getSquad` both take the same shared `sortQuery` parameter, whose description gives example values `"name"`, `"club"`, `"position"`, `"fantasyPoints"`, `"minutesPlayed"`, `"gamesPlayed"`. Neither consuming schema (`DraftPlayerPoolEntry`, `SquadPlayerView`) has fields with those exact names — both actually use `playerName`, `clubId`, `position`, `seasonFantasyPoints`, `seasonMinutesPlayed`, `seasonGamesPlayed`. This client sends the *schema* field names (e.g. `sort=seasonFantasyPoints`) on the reasoning that a `sort` parameter should reference the field it's sorting by in the response it's sorting — but the parameter description's own examples suggest the backend might instead expect the shorter aliases. This is unconfirmed either way and affects both Draft Board (§2.1's mapping) and Squad (built against the same assumption) identically — verify against the running API which convention the backend actually implements, and correct both call sites together if it turns out to be the aliases rather than the schema names.

## 2.3k No "current Gameweek" endpoint either — the fourth instance of the same pattern (found implementing F-UI-003.1, v1.5)

Consistent with §2.3d (current EPL season) and Draft Board's current-draft/current-season lookups: nothing in the spec identifies "the current Gameweek." `useCurrentGameweek` (`src/api/hooks/useEpl.ts`) infers it as whichever Gameweek's `rosterLockDeadline` hasn't passed yet, falling back to the season's last Gameweek. Recorded briefly rather than as a full new subsection, since it's the same underlying gap already documented three times over — the pattern itself ("no endpoint says what's current, infer it from a deadline/status field") is now the established convention for this codebase, not a new discovery each time.

## 2.3l `LeagueMessage` has no category field — Dashboard's "news feed" is really just the Messages feed, minus a tag (found implementing F-UI-003.1, v1.5)

BRD UIR-038 describes a news feed where "each item shows a category tag" (the mock-up used Admin/Injury/Result). `LeagueMessage` is `{ leagueMessageId, leagueId, authorMembershipId, body, publishedAt }` — there is no category/tag field, and no separate "league activity" or "news" endpoint distinct from plain admin-authored messages exists anywhere in the 71-endpoint surface. The mock-up's Injury and Result "news" items look like they were meant to be system-generated activity entries, not administrator-typed messages, but nothing in the backend actually generates or serves that. **Scope decision**: Dashboard's news feed renders the real League Messages feed (author's username, body, relative timestamp), newest first, with no category tag — there is nothing to tag it with. Resolving UIR-038 as written would need a backend addition: either a `category`/`eventType` field on `LeagueMessage`, or a genuinely separate system-activity feed endpoint.

## 2.3m `HeadToHeadMatch` has no per-match kickoff-time field (found implementing F-UI-003.4, v1.7)

`HeadToHeadMatch` is `{ matchId, seasonId, gameweekId, homeFantasyTeamId, awayFantasyTeamId, homeScore, awayScore, result, leaguePointsHome, leaguePointsAway }` — no kickoff time. The mock-up's Schedule screen showed a distinct time per row ("Sat 12:30", "Sat 15:00", ...), but a H2H match doesn't have its own kickoff — it resolves whenever that Gameweek's real EPL fixtures happen, which is genuinely one shared window, not several distinct ones. This client computes a single Gameweek-level "first kick-off" time from `getGameweekFixtures` (the same computation already used on Lineup and Dashboard) and shows that same value on every unresolved match in that Gameweek, rather than fabricating a different time per row the way the mock-up did. Fetched only for Gameweeks that actually have an unresolved match, not unconditionally for every Gameweek tab.

## 2.3n No bulk "list every FantasyTeam's Season Goal Prediction" endpoint — and the reveal-until-season-end rule is enforced by this client, not the API (found implementing F-UI-003.5, v1.8)

`getSeasonGoalPrediction` is per-`fantasyTeamId` only — there is no League- or Season-scoped list operation returning every team's prediction in one call, unlike `getStandings`/`listFantasyTeams`. This client fetches the League Predictions list (BRD UIR-083) the same way `usePlayersByIds` (§2.3h context) fetches individual players: one `useQueries`-driven request per `FantasyTeam`. More consequentially, the operation's own `x-authorization` is `FantasyTeamOwnerOrActiveLeagueMember` — meaning any active league member could, as far as the API itself is concerned, read *any* team's prediction value at *any* time, including mid-season. Concealing other managers' values until the season ends (UIR-083, the "hidden until reveal condition" pattern of UIR-031) is therefore purely a UI/business-rule convention this client enforces, not an API-level restriction. **This client enforces it at the request level, not just the display level**: predictions for teams other than the viewer's own are not requested at all until `Season.status === 'Completed'` — see `LeaguePredictionsList` in `src/screens/league/`.

## 2.3o `SeasonGoalPrediction` already carries the exact fields BRD UIR-081/082 need — no client-side reconstruction of lock timing or the final comparison (found implementing F-UI-003.5, v1.8)

`SeasonGoalPrediction` is `{ predictionId, seasonId, fantasyTeamId, predictedEplGoals, submittedAt, lockedAt, finalActualGoals, finalAbsoluteDifference }`. Two things this saves the client from inferring: (1) `lockedAt` records whichever lock moment actually happened for that specific prediction — Season start under normal submission (BR-127/BR-128) or the moment of submission itself under the late-submission fallback (`submitSeasonGoalPrediction`'s own description cites BR-299) — so the client displays the real timestamp UIR-081 asks for rather than assuming every prediction locked at Season start; (2) `finalActualGoals`/`finalAbsoluteDifference` are computed server-side exactly once, at season end (BR-130/BR-131), and stored directly on the record — this client reads them straight off the response for the "Final Comparison" stat rather than deriving its own difference from a season-long goal history, and only computes anything itself for the *in-progress* "Actual EPL Goals So Far" figure (summing `ClubStanding.goalsFor` across `getEplTable`'s response), which has no server-computed equivalent since it isn't a stored fact, just a live sum. The documented `404` on `getSeasonGoalPrediction` ("Not yet submitted") is treated as the legitimate not-yet-submitted state (`data: null`), not surfaced through `ErrorState` — the first place in this client a documented 404 is consumed this way rather than as an error.

## 2.3p `AdministrativeAction` has no dedicated summary/target-player/target-team fields — only untyped `beforeState`/`afterState` and a free-string `targetEntityType` (found implementing F-UI-004.2, v1.9)

`AdministrativeAction` is `{ actionId, leagueId, actingMembershipId (nullable), actionType, targetEntityType: string, targetEntityId, beforeState: object (additionalProperties: true), afterState: object (additionalProperties: true), reason (nullable), createdAt }`. Two real gaps against BRD UIR-127/131/132's expectations: (1) `targetEntityType` has no `enum` in the spec — there is no confirmed, enumerated set of values (`"Player"`? `"FantasyTeam"`? something else entirely?) this client can safely branch on to resolve a friendlier label (a player's name, a team's username) the way it can for, say, a Squad row's `playerId`; (2) `beforeState`/`afterState` are **completely untyped** — `additionalProperties: true` means literally any shape is valid, and nothing in the spec documents which keys to expect per `actionType`, so a hardcoded "Summary" sentence per action type (as the mock-up/BRD illustrate — e.g. UIR-132's "marked season-ending · replacement-eligible" phrasing) would be an unconfirmed guess that could silently render nothing useful the moment a real payload's keys didn't match. **Resolution adopted for this pass**: the "Target" column shows `targetEntityType` as-is (with the full `targetEntityId` available on hover) except for `ConfigurationChanged`, where UIR-131 itself dictates the literal label "League Settings" regardless of the raw field values; the "Summary" column is a **generic before/after key diff** — every top-level key that differs between `beforeState` and `afterState` renders as `key: before → after` — rather than per-`actionType` hardcoded phrasing (see `src/screens/admin/auditFormat.ts`). This degrades gracefully for every `actionType` including ones with no documented convention at all (`Other`), and the full untyped objects remain available verbatim in each row's expanded before/after detail (UIR-020/UIR-128) as ground truth regardless of what the generic diff manages to summarize. Confirming the real `targetEntityType` string values and `beforeState`/`afterState` key conventions against the running API would let a future revision replace the generic diff with genuinely friendly, UIR-132-style phrasing per action type.

## 2.3q The team-scope filter (UIR-126) can only offer the *current Season's* FantasyTeams — Audit Log itself is not Season-scoped at all (found implementing F-UI-004.2, v1.9)

`getAuditLog` is purely League-scoped (no `seasonId` parameter, no Season filter of any kind) — its `fantasyTeamId` filter parameter accepts any FantasyTeam id ever created in that League, across every Season, plus the `"__league_settings__"` sentinel for rows with no owning team. But the only way this client can *list* FantasyTeams to populate the scope dropdown is `listFantasyTeams(leagueId, seasonId)` — a Season-scoped operation — and there is no League-wide "every FantasyTeam this League has ever had" endpoint. **Scope decision for this pass**: the Team/Scope dropdown offers only the active League's current-Season FantasyTeams, consistent with how every other team-listing surface in this client already works. A user wanting to filter Audit Log by a team from a *prior* Season has no dropdown option for it — a real, if narrow, gap, since the underlying data the filter would query is not itself Season-restricted. Properly resolving this would need either a League-wide FantasyTeam-listing endpoint or this client fetching and merging `listFantasyTeams` across every one of the League's Seasons, which isn't justified by this pass alone.

## 2.3r There is no endpoint to list or browse `ScoreOverride` records at all (found implementing F-UI-004.3, v1.10)

`createScoreOverride` (`POST /admin/score-overrides`) and `undoScoreOverride` (`POST /admin/score-overrides/{scoreOverrideId}/undo`) each return only the single `ScoreOverride` object they just acted on — there is no `GET /admin/score-overrides`, no League- or Season-scoped listing, nothing. BRD UIR-139's "Active Overrides table (league-wide)" and UIR-141's "Recently Undone table" have no dedicated data source whatsoever. **Resolution adopted**: both tables are reconstructed from Audit Log's own `ScoreOverride`/`ScoreOverrideUndo` entries (`getAuditLog` filtered by `actionType`, one call per type) rather than left unbuilt — and this isn't really a workaround so much as following BRD UIR-143's own framing directly: "this screen and the Audit Log are two views into overlapping, not independent, data." An override's `targetEntityId` is treated as the corresponding `scoreOverrideId` needed to call `undoScoreOverride` (an inference in the same "unconfirmed but reasonable" spirit as §2.3h/§2.3p, since nothing confirms `targetEntityType`'s exact value for these two action types) — a create action with no later undo action sharing its `targetEntityId` is "active"; one with a matching later undo action is "recently undone." This reuses the exact same generic before/after diff (§2.3p, `auditFormat.ts`) rather than assuming any particular shape for the override's own `originalValue`/`overrideValue` fields inside the audit trail. Each table in this pass reads only a single page (200 rows, the documented max) per action type rather than paginating further — a real, if narrow, limitation if a league ever accumulates more than 200 of either type; Audit Log itself (which does paginate) remains the place to see full history beyond that.

## 2.3s There is no `PlayerPerformance` lookup endpoint anywhere in the 71-endpoint surface — the single most consequential finding in this project so far (found implementing F-UI-004.3, v1.10)

`playerPerformanceId` appears in exactly two places in the entire spec: as a property of `ScoreOverride` and as a required property of `ScoreOverrideRequest`. There is no `PlayerPerformance` schema, no endpoint that returns one, and no endpoint that accepts a player id + Gameweek id and returns a matching performance record or its id. This means BRD UIR-136's form — "player and Gameweek shown as context... the current Official FPL value is shown for comparison" — **cannot be built as specified against this API surface at all**, not as a data-shape inconvenience but as a hard blocker: there is nothing to select a player/Gameweek combination against, and nothing to read a "current Official FPL value" from. Compounding this, neither `createScoreOverride` nor its request/response schema carries a `leagueId` anywhere — `x-authorization` states the caller must be "the League Administrator of the override's League," implying the backend derives League scoping from the `playerPerformanceId` itself. Taken together, this operation reads as designed for an administrator who already possesses a `playerPerformanceId` from some out-of-band source (direct database access, a support workflow, a future internal tool), not as a discoverable, self-service UI flow. **Resolution adopted for this pass**: the override form takes a raw `playerPerformanceId` text input (clearly labeled as a raw identifier, not a player picker) plus a single free-text field name and numeric value (since `overrideValue` is itself `additionalProperties: true` with no fixed field list) and an optional reason — this makes the real mutation genuinely callable and testable, while being transparent on-screen (a dedicated banner, not just this document) that the picker and live official-value comparison the original design called for are not implemented, because there is nothing in this API to build them against. Properly resolving UIR-136 as designed needs a new backend capability — at minimum, a way to look up or list `PlayerPerformance` records by player and Gameweek — not a client-side workaround.

## 2.3t `RateLimitRule` has no `scope` or active-status field — only `endpointPattern`/`windowSeconds`/`maxRequests` (found implementing F-UI-004.4, v1.11)

`RateLimitRule` is `{ endpointPattern: string, windowSeconds: integer, maxRequests: integer }` — nothing else. BRD UIR-148 (and the vendored mock-up's own illustrative Rate Limiting table) expects a "Scope" column (per IP, per IP+username, per email, per FantasyTeam, or per authenticated user) and a "Status" column (active/inactive) per rule, neither of which the schema carries. Scope in particular *could* plausibly be reverse-engineered by pattern-matching `endpointPattern` strings against known conventions (e.g., `/auth/login` implies "per IP + username" per the mock-up's own illustrative row) — but that would be exactly the kind of unconfirmed, hardcoded guess this client has deliberately avoided elsewhere (§2.3j, §2.3p) the moment a real endpoint pattern doesn't match the guessed convention. **Resolution adopted**: the Rate Limiting table renders `endpointPattern`, `maxRequests`, and a formatted `windowSeconds` from real data, with Scope and Status columns explicitly marked "Not exposed by this endpoint" rather than inferred. Properly resolving UIR-148 needs `scope` and an active-status field added to `RateLimitRule` itself.

## 2.3u `SecurityEvent.eventType` has exactly one enum value — no Login/Password-Reset/General-API category breakdown (found implementing F-UI-004.4, v1.11)

`SecurityEvent` is `{ securityEventId, eventType: enum [RateLimitBlocked], endpoint: string, scope: string, detail: string, occurredAt }`. BRD UIR-149 (and the mock-up) expects each event "tagged by category (Login, Password Reset, General API)" — but `eventType` has only ever the single literal value `RateLimitBlocked` in the spec; there is no field that distinguishes *which kind* of rate-limited action occurred. The `endpoint` field (a raw string, presumably an endpoint path) could theoretically be pattern-matched into a category the same unconfirmed way `RateLimitRule.endpointPattern` could — rejected for the same reason as §2.3t. **Resolution adopted**: each event row shows the raw `endpoint` value in place of a category tag (still identifying, in the caller's own words, what was hit), alongside the real `scope` and `detail` strings (which already carry the substance of BRD UIR-149's "plain-language description" and "outcome" — e.g., "blocked for 15 minutes" — as free text) and a relative timestamp from `occurredAt`. No category taxonomy is fabricated. Properly resolving UIR-149 as designed needs either an enumerated, richer `eventType` or a dedicated `category` field on `SecurityEvent`.

Two things on this screen are **not** findings, despite having no dedicated endpoint, because they were never expected to be data-driven in the first place: the three auth-posture tiles (UIR-146 — "Bearer JWT," the 15-minute access-token/30-day refresh-token lifetimes) are the platform's own already-documented, real architectural facts (Architecture v1.2 §7.2, and the vendored mock-up's own Security screen states the identical values), not something any endpoint was ever going to expose; and the Security Checklist (UIR-150) is inherently a static list of governing `BR-###` citations, the same category of content as Username Display Policy's "resolved decision" framing (F-UI-004.5, confirmed out of scope for an endpoint back in the v1.0 mapping table).

## 2.3x `acceptInvitation`'s `410` carries no structured cause field — expired, already-accepted, and revoked are indistinguishable client-side (found implementing F-UI-001.8, v1.13)

The `acceptInvitation` operation's `410` response is a bare `ProblemDetails` with a free-text `detail` string ("Invitation expired, already accepted, or revoked") and no enumerated `errorCode` values for this operation the way, e.g., `player_already_owned` is documented for `makeDraftPick` (§6 of this document). There is no way for this client to reliably distinguish which of the three causes actually occurred without parsing `detail` as free text — which this client deliberately does not do, for the same reason it doesn't parse `endpointPattern`/`targetEntityType` strings elsewhere (§2.3p, §2.3t): an unconfirmed string-matching guess would silently break the moment the backend's wording changed. **Resolution adopted (BRD UIR-189)**: Accept League Invitation shows one generic "this invitation is no longer valid" message for all three causes, rather than inventing a false three-way distinction. Confirming real `errorCode` values for this operation (mirroring the convention already established for `makeDraftPick`/`submitGameweekRoster`) would let a future revision offer a more specific message per cause.

## 2.3y `listMyLeagues` is confirmed caller-scoped — used directly to resolve "does this user have zero leagues" (found implementing F-UI-001.5, v1.13)

Confirmed by its own summary: "List Leagues the caller has an active LeagueMembership in" — genuinely scoped server-side, not a platform-wide list this client would need to filter itself. This matters because `ActiveLeagueContext` (Architecture, pre-existing) still only holds a hardcoded two-league placeholder list pending its own separately-tracked rewiring — it cannot answer "does this real, just-authenticated user actually belong to any league at all," which BRD UIR-177 needs answered correctly (an empty-leagues empty state vs. a Dashboard redirect). `usePostAuthDestination` (`src/state/`) calls `listMyLeagues` directly for this one decision rather than waiting on that broader rewiring, and calls `setActiveLeagueId` with whatever real league id it finds so the shell's switcher/nav reflects it — though until `ActiveLeagueContext` itself is rewired to real membership data, its own `activeLeague` name lookup only resolves a display name for the two placeholder leagues, a pre-existing limitation this pass didn't need to and didn't attempt to fix.

## 2.3z `Invitation` carries no `channel` field — only the send-side request does (found implementing F-UI-001.11, v1.14)

`Invitation` (returned by both `createInvitation` and `listInvitations`) is `{ invitationId, leagueId, seasonId, destination, status, createdAt, expiresAt }` — no `channel`. `channel` (`Email`/`Sms`) exists only on `CreateInvitationRequest`, the request body a League Administrator submits when sending one; it is not persisted onto (or at least not returned on) the resulting record. This means Invitations' pending/expired/revoked list (BRD UIR-205) cannot show which channel a past invitation was sent through — the column simply isn't in the response, not a rendering gap this client could close by asking differently. **Resolution adopted**: the list omits a Channel column entirely rather than guessing or leaving a blank one; Channel remains only a field on the send form itself, where the administrator is the one choosing it in the moment.

## 2.3aa No backend mechanism for administrator transfer exists, mirrored at the API level (found implementing F-UI-001.12, v1.14)

Same underlying gap BRD §12 item 13/DEC-UI-043 already records at the requirements level, noted here too for completeness in this document's own reconciliation trail: `leaveLeague`'s `409` response text ("the sole League Administrator cannot leave without first transferring administration") is the only place in the entire 71-endpoint surface that references a transfer capability, and nothing — no request field on any operation, no separate endpoint, no schema property — actually implements one. `useLeaveLeague` (`src/api/hooks/useLeagueSeason.ts`) calls the real endpoint and lets this exact `409` surface as a specific, honest message (BRD UIR-211) rather than working around a capability gap that has no client-side workaround available at all.

# 3. Feature-to-Operation Mapping

## 2.3v There is no endpoint to check any user's retirement status except the caller's own — UIR-098's "tagged as retired" requirement isn't implementable (found implementing F-UI-004.6, v1.12)

`UserStatus` (`Active | Retired`) exists only on `UserSelfDto`, returned by `GET /users/me` — there is no `GET /users/{userId}` or any other operation that returns a `status` for a user other than the caller. The closest thing, `POST /admin/users/{userId}/reactivate`, is a System-Administrator-only *write* action with no safe, side-effect-free way to use it as a status probe, and it isn't available to an ordinary league member viewing History anyway. This means BRD UIR-098's "must still display correctly, tagged as retired" requirement has no data source to satisfy it — History cannot show a "Retired" badge next to any historical manager's name, regardless of whether that manager has actually retired. **The other half of UIR-098 already holds without any special-casing**: every join this client performs — `fantasyTeamId`, `leagueMembershipId`, `userId` — has always been by internal id, never by matching a username string (the same convention established for `FantasyTeam.username`, BRD DEC-UI-015), so a retired manager's historical record genuinely cannot be confused with a different, later user who reuses their old username (BR-012, BR-298); it just isn't visibly labeled. Resolving the labeling half needs a backend addition — at minimum, a way to read any user's `status` by id (or a `LeagueMembership`-level "user is retired" flag), scoped appropriately so it isn't a blanket user-directory lookup.

## 2.3w `listDraftSelections` isn't filterable by team; a draft pick's club is resolved via that team's own Squad, not `Player.currentClubId` (found implementing F-UI-004.6, v1.12)

Two related, minor notes rather than a hard blocker: (1) `listDraftSelections` returns every pick for a `draftId` with no `fantasyTeamId` filter parameter, so History's Draft History view (like Draft Board's Recent Picks panel before it) fetches the whole page and filters client-side — consistent with the existing convention, just noted here since History's team-selector UX depends on it explicitly (switching teams re-filters an already-fetched list, not a new request). (2) `Player.currentClubId` is explicitly documented as *current* — a transferred player's historical draft pick would show their club as of today, not as of that pick, if resolved through `Player` directly. This client instead resolves Draft History's (and Gameweek Roster's) player/club identity through that team's own `getSquad` response for the historical season (`SquadPlayerView.clubId`), the same cross-reference already established for Lineup/Squad — `SquadPlayerView`'s own point-in-time semantics for `clubId` aren't explicitly confirmed by the spec either, but it's the same trusted source already used everywhere else in this client for this exact purpose, not a new, separately-unconfirmed assumption.

# 4. Pagination Contract

Three operations are cursor-paginated: `listDraftSelections`, `getAuditLog`, `getSecurityEvents`. Each takes shared `limit` (default 50, max 200) and `cursor` query parameters and returns a `{ items: [...], nextCursor: string | null }` page shape (`DraftSelectionPage`, `AdministrativeActionPage`, `SecurityEventPage` respectively). **This corrects an implicit assumption in Architecture v1.0 §11**, which described a page-size default and a "Load more" UI pattern but didn't specify the pagination *mechanism* — it is cursor-based, not offset/page-number-based. TanStack Query's `useInfiniteQuery` should use `nextCursor` as its `getNextPageParam`, not a computed offset. No other list-returning operation in the spec (`listMemberships`, `listInvitations`, `listFantasyTeams`, `listDrafts`, `listSeasons`, `getStandings`, `listClubs`, `listPlayers`) is paginated — these return full arrays, consistent with their expected size staying small (a league's membership count, a season's fantasy-team count, etc.). **Confirmed workable as implemented (v1.9)**: Audit Log (`src/api/hooks/useAuditLog.ts`) is the first of the three to actually build a real "Load more" UI atop `useInfiniteQuery` with `nextCursor` — Draft Board's `listDraftSelections` consumption fetches only a single fixed-size first page (its Recent Picks panel never needed more), so this is the first place the cursor contract described here is exercised beyond a single page. Security's `getSecurityEvents` consumption (v1.11, `useSecurityEvents`) also stays single-page, for the same reason as Draft Board — a "recent events" glance (BRD UIR-149) doesn't call for a "Load more" affordance the way Audit Log's AC10 explicitly does. History's Draft History view (v1.12) requests `listDraftSelections` at the documented 200-row max (via `useDraftSelections`'s new optional `pageSize` parameter) rather than the default 50, since it needs the *whole* draft's picks to filter by team client-side — still a single page, not "Load more," so a season whose combined squad sizes exceed 200 picks would silently truncate; noted as a real but narrow limitation rather than built around with full pagination.

# 5. Idempotency & Optimistic Concurrency Contract

| Operation | Idempotency-Key | If-Match (ETag) | Behavior on conflict |
|---|---|---|---|
| `makeDraftPick` | Required | Not used | `409 player_already_owned` if another team's concurrent pick for the same player won the race first. |
| `submitGameweekRoster` | Required | Required (from the preceding `getGameweekRoster`'s `ETag` response header) | `409` on a stale `If-Match` (someone/something changed the roster since the client's last read — e.g., an admin correction) — the client must refetch and prompt the user to reconcile, not blindly retry with the stale ETag. `409 season_goal_prediction_required` is a *different* 409 cause on this same operation (see §6) and must be distinguished by `errorCode`, not assumed to mean a concurrency conflict. |
| `setCaptain` | Not used | Not used | `409` only if the roster is already `Locked` (`BR-040`) — no concurrency token because this is a narrower, single-field mutation with its own simpler failure mode. |
| `correctRoster`, `createScoreOverride`, `undoScoreOverride`, `extendDraftTimer` | Not used | Not used | Administrator-only actions; the spec does not model concurrent-administrator conflicts for these today. |

Every `Idempotency-Key` the client sends must be a freshly generated UUID **per user-initiated action**, not reused across retries of what the user perceives as "the same click" versus a genuinely new submission — Architecture v1.1 §6.5 specifies exactly where in the mutation-hook lifecycle it's generated.

# 6. Known Error Codes Requiring Distinct UI Treatment

The generic `ErrorState` component (Architecture §10) handles any `ProblemDetails` body by showing `detail` and `correlationId`. The following `errorCode` values, however, are specifically named in the spec's operation descriptions and correspond to conditions the BRD already has an opinion about — these must be caught and handled with their own copy, not the generic fallback:

| `errorCode` | Operation | Surfaces as |
|---|---|---|
| `player_already_owned` | `makeDraftPick` | "That player was just taken — refreshing the pool" (auto-refetch the pool, don't just show a raw error) |
| `season_goal_prediction_required` | `submitGameweekRoster` | Directly implements BRD UIR-087's disclosed consequence — must route the user toward Season Predictions, not show a generic validation error. |
| `invalid_roster_composition` | `submitGameweekRoster` | Should render inline against the positional checklist (BRD UIR-045), telling the user which minimum is unmet — the checklist already shows this proactively (Architecture should make submission client-side-block on it, per BRD UIR-045's "enforces" language, so this server error becomes a rare defense-in-depth case rather than the primary path). |

Any `errorCode` not in this table falls back to the generic `ErrorState` treatment; this table should grow as the running API's actual error catalog is confirmed (the spec does not enumerate every possible `errorCode` value exhaustively — `player_already_owned` is given as an example in `ProblemDetails.errorCode`'s own schema description, not an exhaustive enum).

| DEC-UI-021 | (v1.6) Lineup computes every player's opponent client-side from `getGameweekFixtures`, rather than reading `RosterPlayer.opponentClubId`/`opponentIsHome` from the roster response. | Those fields only exist for players the server already knows are in the roster; a reserve being considered for addition (not yet submitted) has no such field to read, so one client-side computation covering every squad player uniformly is simpler and more consistent than switching sources depending on a player's roster status. |

| DEC-UI-023 | (v1.7) Schedule fetches the whole season's H2H schedule in one unfiltered `getSchedule` call and groups it client-side by Gameweek, rather than one filtered call per Gameweek tab. | Cheaper (one request, not N) and directly satisfies BRD UIR-073 (future Gameweeks already loaded, not revealed only when selected) as a side effect of the fetching strategy rather than needing separate handling. |
| DEC-UI-024 | (v1.7) Every unresolved match in a Gameweek shows the same Gameweek-level first-kickoff time, not a fabricated distinct time per match. | §2.3m: `HeadToHeadMatch` has no per-match kickoff field, and a H2H match's timing is genuinely tied to the whole Gameweek's real fixtures, not to itself individually — showing one honest shared value beats inventing several different ones. |

| DEC-UI-026 | (v1.8) The "Final Comparison" stat reads `finalActualGoals`/`finalAbsoluteDifference` directly off the `SeasonGoalPrediction` record once populated, rather than this client deriving its own difference from a season-long goal history. | §2.3o: the backend already computes and stores this once, authoritatively, at season end (BR-130/BR-131) — recomputing it client-side would be redundant and a possible source of drift from the backend's own value. |
| DEC-UI-027 | (v1.9) Audit Log's "Summary" column is a generic before/after key diff across `beforeState`/`afterState`, not hardcoded per-`actionType` phrasing; "Target" shows the raw `targetEntityType` (except `ConfigurationChanged`, which UIR-131 dictates literally as "League Settings"). | §2.3p: both fields are completely untyped in the spec (`additionalProperties: true`, no `targetEntityType` enum) — a hardcoded per-type summary would be an unconfirmed guess that could silently show nothing useful against a real payload; a generic diff degrades gracefully for every type, including ones with no documented convention, and the raw objects are always available in the expanded detail as ground truth. |

| DEC-UI-029 | (v1.10) Score Corrections' Active/Recently-Undone tables are reconstructed from Audit Log entries (`actionType=ScoreOverride`/`ScoreOverrideUndo`), matched by a shared target id, rather than left unbuilt. | §2.3r: no override-listing endpoint exists at all; BRD UIR-143 already frames Score Corrections and Audit Log as overlapping views of the same underlying data, which validates this as the intended architecture rather than an ad hoc workaround. |

| DEC-UI-047 | (v1.14) League Settings excludes `tieBreakRulesetVersion` from its editable configuration fields. | It's an internal implementation identifier (ADR-008's "default ruleset identifier"), not a business-facing policy value like every other `BR-291` parameter — a free-text field for it would let an administrator reference a non-existent ruleset version with no way for this client to validate it. |
| DEC-UI-048 | (v1.14) Invitations' pending/expired/revoked list has no Channel column. | §2.3z: `Invitation` doesn't return a `channel` field at all, only `CreateInvitationRequest` (the send-side request) does — there's nothing to display, not a gap this client's rendering choices could close. |
